# Vision: Game Backend-as-a-Service (BaaS)

## Концепция проекта
Проект плавно эволюционирует из высокопроизводительной in-memory базы данных в полноценную инфраструктурную платформу **Backend-as-a-Service (BaaS) для инди-игр и Web3/Fintech проектов**. 

Идея заключается в том, чтобы занять "золотую середину" между свободой Steam и серверным удобством Roblox:
* Разработчики создают игры на любых графических движках (Unity, Unreal Engine).
* Вся сложная серверная логика (экономика, матчмейкинг, защита транзакций, реал-тайм стейт) перекладывается на нашу платформу через удобный SDK.

## Почему это сработает? (Проблема рынка)
Инди-разработчики умеют делать красивую графику и интересный геймплей. Но создание надежного бэкенда, который выдержит миллионы игроков, защитит экономику от дюпов (читерского копирования) и обеспечит низкий пинг — это непреодолимый барьер для многих студий.
Текущие монополии либо не дают бэкенд "из коробки" (Steam), либо забирают до 75% дохода и заставляют использовать только свои внутренние инструменты (Roblox). 
Наша платформа работает по модели B2B (продажа "лопат" разработчикам) и берет на себя всю серверную головную боль за честную микрокомиссию с транзакций.

## Роль `storage_in_memory` в Архитектуре
Текущий проект `storage_in_memory` выступает **идеальным высоконагруженным Ядром (Core Engine)** для этой платформы:

1. **Экономика и Микротранзакции (Hot Wallet / L2 Layer):** 
   * *Задача:* Атомарные списания/начисления валюты, безопасная покупка предметов, обработка микро-выплат.
   * *Как решает KVStore:* Lock-free архитектура шардов, кастомный TCMalloc-аллокатор и Epoll-сеть обеспечивают обработку миллионов RPS без задержек. Строгая консистентность в памяти гарантирует отсутствие гонок данных (data races) и дюпов.

2. **Игровые сессии и Лобби (Real-time State):**
   * *Задача:* Матчмейкинг, хранение эфемерного стейта матчей, статусы присутствия игроков (online/offline).
   * *Как решает KVStore:* Механизм TTLManager (Time-To-Live) обеспечивает автоматическую очистку завершенных сессий, а zero-allocation подход спасает от GC-пауз, сохраняя идеальный пинг для игроков.

3. **Социальные взаимодействия:**
   * *Задача:* Глобальные и групповые чаты, реал-тайм уведомления о событиях в игре (кто-то купил редкий меч).
   * *Как решает KVStore:* Встроенный высокопроизводительный Pub/Sub брокер сообщений.

4. **Умный матчмейкинг и рекомендации:**
   * *Задача:* Подбор игроков по уровню навыка (MMR) или интересам, рекомендация кастомных миров (UGC).
   * *Как решает KVStore:* Векторный индекс (Vector HNSW) позволяет быстро находить ближайших соседей по многомерным параметрам.

## План развития (Roadmap)
Чтобы превратить базу данных в Платформу, необходимо нарастить инфраструктурный слой поверх ядра:

1. **Фаза 1: Core Database (Текущий этап)**
   * Стабилизация кастомного аллокатора TCMalloc.
   * Интеграция паттернов финтеха (Hot Buffer Outbox) для асинхронного сброса финансовых транзакций из in-memory в надежное "холодное" хранилище (PostgreSQL) для обеспечения ACID-надежности.

2. **Фаза 2: API Gateway (Внешний шлюз)**
   * Создание прослойки (HTTP / gRPC / WebSocket), которая торчит в интернет и принимает запросы от игровых клиентов.
   * Авторизация запросов по API-ключам игр.
   * Безопасная трансляция внешних запросов во внутренний бинарный RESP-протокол для общения со `storage_in_memory`.

3. **Фаза 3: Developer SDKs**
   * Разработка легковесных библиотек для игровых движков: C# (для Unity), C++ (для Unreal Engine). 
   * Предоставление простых методов-оберток (например, `Platform.Economy.BuyItem(itemId, price)`).

4. **Фаза 4: Developer Dashboard**
   * Веб-панель управления для инди-разработчиков.
   * Настройка каталога предметов (ID, цены, характеристики), просмотр аналитики онлайна, RPS и доходов. Вывод заработанных средств.
