# 🎤 Презентация проекта: KVStore → Molten

> Сценарий выступления + тезисы для слайдов. Рассчитан на ~12-15 минут.
> Работает и для технической, и для смешанной аудитории: технические детали вынесены
> в «глубину» — раскрываешь по реакции зала. Слоган проекта: **«The cache that thinks.»**

---

## Лифт-питч (60 секунд — выучить наизусть)

> «Представьте типичную высоконагруженную систему: сервис, рядом Redis для кэша, рядом Kafka
> для событий. Каждая операция — 3-4 сетевых хопа между процессами, проблемы
> консистентности, латенси в миллисекундах.
>
> Molten схлопывает это в один процесс. Данные, бизнес-логика и события — вместе.
> Это Redis-совместимое in-memory хранилище на Go, но с тремя вещами, которых у Redis нет:
> встроенный векторный поиск, WASM-вычисления прямо в движке и собственный аллокатор,
> убирающий паузы сборщика мусора.
>
> Результат: операция вроде fraud-скоринга проходит за <100 микросекунд вместо
> миллисекунд, потому что нет ни одного сетевого хопа. Один бинарник, ноль зависимостей,
> `redis-cli` работает из коробки.»

## Структура выступления (слайды + что говорить)

### Слайд 1 — Титул
- **На экране:** «Molten — The cache that thinks». Имя, одна строка: «Programmable in-memory
  engine: State + Compute + Messaging в одном процессе».
- **Говоришь:** представляешься, одна фраза что это и зачем.

### Слайд 2 — Проблема
- **На экране:** диаграмма «классический путь»: Client → API → Service → Redis → Kafka.
  Подписи: «4 сетевых хопа · 3 процесса · 5-15 ms · проблема консистентности».
- **Говоришь:** «В любой real-time системе состояние, логика и события живут в разных
  процессах. Это сеть, латенси и рассинхрон. Я задался вопросом: что если положить их в
  один процесс?»

### Слайд 3 — Решение (the big idea)
- **На экране:** диаграмма «Molten путь»: один прямоугольник, внутри KV + WASM + Pub/Sub,
  снизу WAL. Подпись: «0 сетевых хопов · 1 процесс · <100μs · атомарность».
- **Говоришь:** «Один движок объединяет три роли. Логика выполняется там же, где лежат
  данные. Пример — на следующем слайде.»

### Слайд 4 — Живой сценарий (fraud scoring)
- **На экране:** 4 строки:
  ```
  WASM.LOAD fraud_scorer ./model.wasm
  WASM.TRIGGER SET "tx:*" fraud_scorer score_transaction
  SET tx:123 '{"amount":100,"user":"u789"}'
  → читает профиль · считает score · пишет результат · публикует алерт — всё <100μs
  ```
- **Говоришь:** «Бизнес просто делает SET. Триггер сам читает профиль из KV, считает score,
  пишет результат и шлёт событие — без единого сетевого вызова наружу.»

### Слайд 5 — Архитектура (карта слоёв)
- **На экране:** стек слоёв сверху вниз:
  `Epoll-сеть (zero-alloc)` → `RESP-протокол` → `Диспетчер команд` →
  `[ TCMalloc Store | WAL | TTL | Pub/Sub ]` → `[ Vector (HNSW+LSM) | WASM | AI | Cluster ]`.
- **Говоришь:** проходишь снизу-вверх по запросу за 30 сек. Точка входа — один `main.go`.
  Подчёркиваешь сквозной принцип: **zero-allocation на горячем пути**.

### Слайд 6 — Что внутри: 3 инженерных «фишки»
Выбери 3 истории — это ядро выступления. Для каждой: проблема → решение → цифра.

**(А) Zero-GC через собственный аллокатор**
- Проблема: GC сканирует миллионы мелких объектов → latency spikes.
- Решение: TCMalloc-аллокатор (per-worker MCache, lock-free) + pointer-free структуры
  (uint32-смещения в плоские арены).
- Цифра: **GET 17.9 ns, 0 аллокаций ≈ 55M чтений/сек на ядро.**

**(Б) Векторный поиск как LSM-дерево**
- Проблема: обычный HNSW — мутабельная структура, вставка блокирует поиск.
- Решение: LSM-подход (как RocksDB) — вставка O(1) в delta, фоновая компакция в
  иммутабельные HNSW-сегменты, поиск без локов и параллельно по сегментам.
- Цифры: **recall@10 ≈ 0.966 @ efSearch=100** (рабочая точка на recall/QPS-кривой),
  **SQ8-квантование: 4× меньше памяти при 96% recall.**

**(В) Сеть: pipeline дал 37×**
- Проблема: TCP round-trip на каждую команду — главный bottleneck.
- Решение: drain всех команд из одного пакета + один Flush.
- Цифра: **GET 65K → 2.42M RPS (37×).** Урок: измеряй bottleneck до оптимизации.

### Слайд 7 — Результаты (таблица бенчмарков)
- **На экране:**
  | Метрика | Значение |
  |---|---|
  | GET (single, lock-free) | 17.9 ns · 55M/сек·ядро |
  | GET / SET (pipeline) | 2.42M / 1.35M RPS |
  | WAL запись (batched) | 137.8 ns · 0 allocs · ~7M/сек·ядро |
  | Восстановление из WAL | ~1.5M записей/сек |
  | Vector recall@10 | 0.966 @ efSearch=100 |
  | SQ8 компрессия | 4× память / ~96% recall |
- **Говоришь:** «Каждый перф-PR подкреплён бенчмарком — regression латенси у меня P0-баг.»

### Слайд 8 — Где это применимо
- **На экране:** FinTech (fraud <5ms) · AdTech (RTB <10ms) · GameDev (state+events) ·
  IoT/Edge (лёгкий ARM-бинарник) · RAG/семантический поиск (векторы + AI).
- **Говоришь:** одна-две фразы про нишу: «пересечение in-memory + streaming + WASM, где
  Redis/Kafka по отдельности не закрывают».

### Слайд 9 — Конкурентное позиционирование
- **На экране:** таблица: Redis / Tarantool / Redpanda / **Molten**, строки:
  In-Memory KV · Zero-GC · Broker · Programmable(WASM) · Redis-совместимость · Single binary.
  Molten — единственный с галочками во всех.
- **Говоришь:** «Уникальная комбинация: State + Compute + Broker в одном процессе на Go.»

### Слайд 10 — Итог + дорожная карта
- **На экране:** «Сделано: ядро, векторы, WASM, кластер, observability. Дальше: Raft-консенсус,
  multi-tenant SaaS, мульти-коллекции векторов.»
- **Говоришь:** честно про текущий статус и 1-2 следующих шага. Закрываешь слоганом.

## Если есть живое демо (60-90 сек)

```bash
# 1. KV + TTL
redis-cli -p 6380 SET hello world
redis-cli -p 6380 GET hello

# 2. Векторный поиск
redis-cli -p 6380 VSIM.ADD doc:1 3 0.1 0.2 0.3
redis-cli -p 6380 VSIM.SEARCH 5 0.1 0.2 0.3        # ← top-K соседей

# 3. Фильтрованный поиск (категоризация)
redis-cli -p 6380 SET category:doc:1 electronics
redis-cli -p 6380 VSIM.SEARCHFILTER 5 category electronics 0.1 0.2 0.3

# 4. WASM-триггер (если подготовлен модуль)
redis-cli -p 6380 WASM.LOADFILE fraud ./fraud_scorer.wasm
redis-cli -p 6380 WASM.TRIGGER SET "tx:*" fraud score_transaction
redis-cli -p 6380 SET tx:1 '{"amount":9999}'        # ← триггер сработает сам
```
- Подстраховка: заранее проверь, что сервер поднят (`make build && ./kvstore-server`),
  команды отрепетированы, есть скриншот на случай сбоя сети/проектора.

## Анти-вопросы из зала (готовые ответы)

- **«Чем лучше Redis?»** → Redis не умеет stateful-вычисления (только Lua), не имеет встроенного
  векторного поиска нужного уровня и Zero-GC. Я не заменяю Redis везде — я закрываю нишу
  «данные+логика+события в одном процессе».
- **«Это production-ready?»** → Ядро, WAL, кластер и observability — да, покрыто тестами под
  `-race`. Чего нет для serious-prod: Raft-консенсус и multi-tenant — это явный roadmap.
- **«Почему Go, а не Rust/C++?»** → Single binary без зависимостей, быстрая разработка, и я
  доказал, что zero-GC дисциплиной можно получить C-подобную латенси без ручного управления
  памятью везде.
- **«Сам писал или с ИИ?»** → Архитектурные решения и trade-offs — мои; могу объяснить любую
  строчку и почему именно так (см. истории про LSM, pipeline, data race).
