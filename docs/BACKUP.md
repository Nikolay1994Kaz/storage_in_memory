# Резервное копирование и восстановление

## Что бэкапим
Всё состояние kvstore лежит в каталоге данных (по умолчанию `./data`):

- `wal_*.log` — Write-Ahead Log, **полный источник правды** (replay восстанавливает
  KV, векторы, zset, TTL);
- `graph_leveled.bin` — снапшот векторного индекса (CRC-защищён, пишется атомарно
  через tmp+rename) — оптимизация старта;
- `snapshot.wal` — снапшот KV — оптимизация старта;
- WASM-модули и триггеры (если используются).

Поскольку WAL самодостаточен, **архив всего каталога = полный бэкап**.

## Консистентность
Бэкап **crash-consistent даже на живом сервере**: снапшоты пишутся атомарно и с
CRC, а частичная хвостовая запись WAL пропускается на replay по CRC. То есть архив
эквивалентен состоянию на момент «краша», которое путь восстановления и так
корректно обрабатывает. Останавливать сервер для бэкапа не требуется.

Для минимального окна на restore можно форсировать свежий снапшот перед бэкапом
(необязательно): `redis-cli -p 6380 COMPACT`.

Полностью durable снимок гарантируется при **штатной остановке** (graceful
shutdown делает fsync последнего батча WAL) — забэкапьте каталог после остановки.

## Создание бэкапа
```sh
make backup                        # data → backups/kvstore-backup-<UTC>.tar.gz
make backup DATA_DIR=/srv/kv/data BACKUP_DIR=/mnt/backups
# или напрямую:
scripts/backup.sh /srv/kv/data /mnt/backups
```

## Восстановление
**Сервер должен быть остановлен.** Прежний каталог не удаляется, а отодвигается в
`<DATA_DIR>.bak.<UTC>`.
```sh
make restore BACKUP=backups/kvstore-backup-20260701T120000Z.tar.gz
# или напрямую:
scripts/restore.sh backups/kvstore-backup-20260701T120000Z.tar.gz /srv/kv/data
```
После распаковки запустите сервер поверх восстановленного каталога — он накатит
снапшот + WAL и продолжит работу.

## RPO/RTO (single-node)
- **RPO** при аварии (не штатная остановка): ≤ интервал fsync WAL (по умолчанию
  ~100 мс, `syncInterval`); при штатной остановке — 0 (fsync последнего батча).
- **RTO**: время распаковки архива + загрузки снапшота + replay «хвоста» WAL.
  Чем свежее снапшот (COMPACT перед бэкапом), тем короче replay.

Всё выше — про **локальные** RPO/RTO. Периодический архив защищает от потери
диска с RPO = интервал бэкапа. Для непрерывной внешней копии см. WAL-shipping.

# Восстановление на момент (`-restore-to-lsn`)

Отдельный режим и отдельная задача: не «поднять базу после аварии», а
**посмотреть, каким состояние было в конкретный момент**. Нужен, когда в память
попало неверное — атакой, галлюцинацией или кривым импортом — и надо понять,
что именно агент считал истиной, когда принимал решение.

```sh
# 1. Найти момент: журнал печатается как есть, ничего не меняя.
kvstore-server -data-dir /srv/kv/data -wal-inspect
# LSN          OP                 KEY
# 1            VSIM.ADDDOC        good1 (313 bytes)
# 5            VSIM.ADDDOC        poison (341 bytes)   ← подсадка
# 9            VSIM.ADDDOC.BATCH  poison (377 bytes)   ← карантин

# 2. Поднять состояние на этот момент (сервер на другом порту).
kvstore-server -data-dir /srv/kv/data -restore-to-lsn 8 -port 6399
```

Два свойства режима, оба обязательны:

- **Только чтение.** Любая запись отклоняется (`READONLY point-in-time
  restore…`), `COMPACT` тоже. Узел, принявший хоть одну запись, порождает
  вторую историю, и дальше уже не отличить её от настоящей.
- **Каталог данных не изменяется побайтово.** Всё, что процесс пишет (новый
  WAL, снапшоты синкера), уходит во временный каталог; WAL-shipping в этом
  режиме молчит, чтобы не затереть настоящую резервную историю.

## Граница: докуда можно отмотать

Снапшоты хранят **состояние, а не историю**, и перезаписываются на месте.
Поэтому отмотать раньше последнего снапшота нельзя — этой истории физически
больше нет. Сервер в этом случае не стартует и называет самый ранний
достижимый LSN:

```
cannot restore to LSN 4: snapshots already hold state past that point
(vector snapshot watermark 9, kv snapshot watermark 9).
The earliest point this data directory can reproduce is LSN 9
```

Практический вывод: **окно восстановления = от последнего снапшота до
настоящего момента**. Чем чаще `COMPACT`, тем короче replay при обычном старте
и тем уже это окно — это прямой размен. Если нужна отмотка глубже, храните
периодические архивы (см. выше): восстановить архив в отдельный каталог и уже
над ним поднять нужный LSN. Удержание базовых снапшотов, которое расширило бы
окно без архивов, не сделано.

# WAL-shipping (continuous, `-ship-url`)

Непрерывная асинхронная доставка durability-набора (WAL-хвост + снапшоты) на
удалённое хранилище — Litestream-подход: погибла VM/диск → восстановление на
любой машине с **RPO ≈ секунды**, без второго живого процесса, репликационного
протокола и failover'а.

## Включение
```sh
# S3-совместимое хранилище (AWS S3 / MinIO / Ceph / LocalStack)
export KVSTORE_S3_ACCESS_KEY=... KVSTORE_S3_SECRET_KEY=...
./kvstore-server -ship-url 's3://bucket/kv-prod?endpoint=https://minio:9000&region=us-east-1'

# или директория (NFS / rclone mount / тесты)
./kvstore-server -ship-url file:///mnt/backup/kv-prod
```
Флаги: `-ship-interval` (период доставки, по умолчанию 1s ≈ RPO при аварии),
`-ship-retain` (сколько restore-точек хранить, по умолчанию 3).

## Восстановление
На новой машине — пустой каталог данных и флаг `-ship-restore`:
```sh
./kvstore-server -ship-restore -ship-url 's3://bucket/kv-prod?...'
```
Сервер скачает последнюю restore-точку (манифест), накатит снапшот + WAL тем же
путём, что при crash recovery, и продолжит работу — включая дальнейший shipping
с той же точки. Поверх существующего состояния restore **отказывается** работать
(защита от затирания) — уберите старый каталог, как это делает `scripts/restore.sh`.

## Как это устроено
Шиппер работает поверх каталога данных, не трогая write-путь:

- `wal_*.log` append-only → хвост уезжает иммутабельными кусками
  `wal/<файл>/<offset>.chunk`;
- `snapshot.wal` / `graph_leveled.bin` иммутабельны после атомарного rename →
  версия целиком под `snap/<fingerprint>/...`;
- каждая консистентная точка фиксируется манифестом (`manifests/<gen>.json` +
  копия `MANIFEST.json`). Манифест публикуется только когда все неактивные
  WAL-файлы доставлены полностью — иначе частичный старый WAL рядом со свежим
  снапшотом воскрешал бы удалённые ключи. Оборванный хвост активного WAL
  отбрасывается на restore по CRC (тот же путь, что crash recovery);
- ретеншн удаляет манифесты старше `-ship-retain` и объекты-сироты.

Ошибки доставки **не блокируют запись** (в отличие от локального durability
fail-stop): это осознанный async-контракт. За отставанием следят метрики —
`kvstore_ship_errors_total`, `kvstore_ship_lag_bytes`,
`kvstore_ship_last_success_timestamp_seconds` (алёрт на возраст обязателен).

## RPO/RTO с shipping'ом
- **RPO при потере машины/диска**: ≈ `-ship-interval` + время загрузки куска;
  при **штатной остановке — 0** (финальный тик после fsync последнего батча).
- **RTO**: скачивание набора + обычный старт (снапшот + replay хвоста).
- Один шиппер на один префикс хранилища: два процесса, пишущие в один
  `-ship-url`, затрут манифесты друг друга.
