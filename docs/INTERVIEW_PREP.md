## 1. Лифт-питч

### Версия на 30 секунд
> «Я построил высокопроизводительное in-memory хранилище на Go — Redis-совместимое,
> но с тремя вещами, которых у Redis нет: встроенный векторный поиск (HNSW поверх
> LSM-дерева), WASM-вычисления прямо в движке и собственный аллокатор в стиле TCMalloc,
> который убирает давление на GC. На пайплайне даёт ~2.4M GET/сек и 1.35M SET/сек на
> одной ноде, с нулём аллокаций на горячем пути.»

### Версия на 2 минуты (добавляешь «почему»)
> «Идея — схлопнуть три процесса в один. В классике: сервис + Redis (кэш) + Kafka
> (события) — это 3-4 сетевых хопа на операцию. Я объединил состояние, вычисления и
> messaging в одном бинарнике: данные и логика в одном процессе, ноль сетевых хопов,
> атомарная консистентность. Например, fraud-скоринг: `SET tx:123` → WASM-триггер читает
> профиль из KV, считает score, пишет результат и публикует алерт — всё за <100μs внутри
> процесса. Ядро написано с философией zero-allocation: epoll-сеть, zero-alloc RESP-парсер,
> собственный аллокатор. Самая интересная часть — векторный движок: я применил LSM-подход
> (как в RocksDB) к HNSW-графам, чтобы вставка была O(1) и не блокировалась тяжёлой
> перестройкой индекса.»

## 2. Архитектурный рассказ за 3 минуты (структура «сверху вниз»)

Рисуешь/называешь слои по ходу. Точка входа всего — `kvstore/cmd/kvstore/main.go`.

1. **Сеть.** Epoll, по event-loop на воркер (`internal/server/epoll.go`). Запрос читается
   в ring-buffer без аллокаций (`connbuf.go`), парсится zero-alloc RESP-парсером
   (`internal/protocol/resp.go`).
2. **Диспетчер.** `executeCommand` в `main.go` — один большой `switch` по командам.
3. **Хранилище.** TCMalloc-аллокатор с per-worker MCache (`internal/store/tcmalloc/`).
   GET — lock-free через хеш-таблицу с linear probing. Зачем своё, а не map+mutex —
   убрать GC и mutex с горячего пути.
4. **Durability.** WAL с батчингом и CRC32 (`internal/wal/`). Фоновый syncer делает
   один fsync на батч из 256 записей. Снапшоты атомарно через `.tmp` + rename.
5. **Векторный движок.** `vector/leveled_store.go` — LSM-структура: delta (горячий слой) +
   иммутабельные HNSW-сегменты по уровням + фоновая компакция. Distance на AVX2-ассемблере.
6. **Над этим:** Pub/Sub (классический + семантический, vector-routed), WASM-движок
   (wazero, reactor-паттерн, триггеры ON_SET/ON_DEL), AI-интеграция (Ollama embeddings),
   кластер (hash-слоты CRC16, gossip, репликация, live-миграция).

Финальная фраза: «Всё это — один бинарник на Go без внешних зависимостей, `redis-cli`
работает из коробки.»

## 3. Вопросы по темам

### 3.1 Go: конкурентность и память

**Q: Зачем свой аллокатор? Чем плох GC у Go?**
- Коротко: При миллионах ключей/векторов GC сканирует миллионы мелких объектов в куче →
  latency spikes. Свой аллокатор хранит данные в плоских аренах → для GC это «числа», а не
  указатели, время сканирования ≈ 0.
- Глубина: В HNSW было `Node{Vector []float32, Neighbors [][]uint64}` — 3M+ слайсов на
  1M нод. Заменил на pointer-free ноду с `uint32`-смещениями в общие арены
  (`VectorArena`, `NeighborsArena`). Бонус — cache locality: соседи лежат подряд, меньше
  cache miss. Файл: `vector/vector_arena.go`, `vector/graph.go`, док `docs/vector_optimization.md`.

**Q: Как сделал lock-free GET?**
- Коротко: Своя open-addressing хеш-таблица с linear probing; чтение идёт по atomic-указателям
  без захвата мьютекса. Запись шардирована per-worker (MCache), поэтому writer'ы не толкаются.
- Глубина: Grow при 70% заполнения, Rebuild для очистки tombstones при 25% удалений.
  Для B+Tree-варианта использовал seqlock'и и deferred free (освобождение памяти после того,
  как все читатели прошли). Файлы: `internal/store/tcmalloc/hashtable.go`, `internal/btree/btree.go`.
- Цифра: GET ~17.9 ns/op, 0 allocs — ~55M чтений/сек на ядро (`docs/PHASE1_BENCHMARKS.md`).

**Q: Какие примитивы синхронизации и почему именно они?**
- `sync.RWMutex` на векторном сторе — много читателей (search), редкие писатели.
- `atomic.Pointer[map[...]]` для tombstones — COW: читатели берут снапшот без блокировки,
  писатель атомарно подменяет указатель. Если удалений нет — указатель nil, нулевой overhead.
- Каналы + семафор (`buildSem`) для координатора компакции (producer-consumer).
- `sync.Cond` для `FlushDeltaSync` (дождаться, пока фоновый воркер сбросит дельту).
- `sync.Pool` для буферов поиска и WAL — переиспользование без аллокаций.
- Файл: `vector/leveled_store.go:267-375` (комментарии к полям struct — лучшая документация).

**Q: Как боролся с data race? Запускал `-race`?**
- Да, тесты проходят под `go test -race`. Главная ловушка: `TCMallocStore` не потокобезопасен
  для конкурентного `Alloc` через общий MCentral/MHeap. Решение: каждый build-воркер компакции
  получает **свой изолированный аллокатор** (`buildAllocators[]`) и уникальный `workerID`.
- Ещё: TOCTOU между `Clear()` и фоновой компакцией закрыл через `compactionEpoch` — воркер
  проверяет поколение под локом перед публикацией сегмента.

### 3.2 Хранилище / TCMalloc

**Q: Расскажи про TCMalloc-аллокатор.**
- Иерархия как в оригинальном tcmalloc: **MCache** (per-worker, lock-free) → **MCentral**
  (на size-class) → **MHeap** (страницы). Size-classes round'ят размер до класса, уменьшая
  фрагментацию. Free идёт через LIFO free-list (горячая память переиспользуется первой).
- Цифра: alloc-only ~109 ns, 0 allocs. Переход с ArenaStore на TCMalloc дал SET +19-41%
  на пайплайне (`docs/optimization_session_summary.md`).
- Файлы: `internal/store/tcmalloc/{mcache,mcentral,mheap,sizeclass}.go`.

**Q: Что делаешь при OOM?**
- `maxmemory` лимит: при `UsedMemory > maxmemory` write-команды отклоняются (`OOM ...`),
  чтения работают. Есть точный учёт памяти для крупных объектов. `main.go` → `s.IsOOM()`.

### 3.3 WAL / Durability

**Q: Как гарантируешь, что данные переживут рестарт?**
- Каждая мутация пишется в WAL **до** ответа клиенту. Восстановление при старте:
  сначала накатывается `snapshot.wal`, потом `wal_*.log` по порядку (`main.go:148-235`).
- Батчинг: клиент пишет в неблокирующий канал (137.8 ns/op, 0 allocs ≈ 7M ops/сек/ядро),
  фоновый flusher собирает до 256 записей, считает один CRC32 и делает **один** `file.Write`
  + fsync. Это group commit. Файлы: `internal/wal/{wal,batch,syncer}.go`.

**Q: Что если сервер упал посреди записи WAL (обрезанный файл)?**
- При чтении граёжно обрабатываю truncation: битый/неполный хвост отбрасывается, CRC32 ловит
  повреждения. Восстановление ~1.5M записей/сек (`docs/wal_benchmarks.md`). Покрыто fuzz-тестом
  `internal/wal/wal_fuzz_test.go`.

**Q: Снапшоты — как делаешь атомарно?**
- Пишу в `*.tmp`, fsync, затем `os.Rename` (атомарен на одной ФС). Старые WAL чистятся после
  успешного снапшота. Векторный индекс сохраняется отдельным бинарником `graph_leveled.bin`.

### 3.4 Векторный движок (центральная часть)

**Q: Зачем LSM поверх HNSW? В чём проблема обычного HNSW?**
- Обычный HNSW: вставка дорогая (перестройка связей), а индекс — единая мутабельная структура,
  которую надо лочить. Под burst-write это убивает latency.
- Моё решение (как RocksDB): вставка = O(1) append в **delta** (горячий буфер). Когда delta
  переполняется — в фоне строится иммутабельный HNSW-сегмент уровня L0. 4 сегмента уровня
  сливаются в один следующего уровня (`fanout=4`). Иммутабельность → search вообще не лочит
  сегменты, читает их параллельно. Файл: `vector/leveled_store.go:19-42` (дизайн в шапке).

**Q: Как удаляешь из иммутабельного сегмента?**
- Tombstones. Удаление помечает ключ в COW-множестве (`atomic.Pointer`), физически вектор
  исчезает при следующем слиянии. Search фильтрует tombstoned-ключи на лету. Если удалений нет
  — overhead нулевой (указатель nil). `leveled_store.go:505` (`Delete`), `:546` (`addTombstone`).

**Q: Как устроен сам поиск?**
- `search` (`leveled_store.go:643`): берёт RLock, собирает снапшот tombstones, компонует фильтр.
  Fast-path: если только delta или один сегмент — без горутин. Иначе — параллельный поиск по
  сегментам (горутина на сегмент при N>3), затем merge top-K через кучу (`heap.go`).
- efSearch — окно поиска; при фильтрации расширяю ×4 для компенсации потери recall.

**Q: Какие оптимизации памяти/скорости в векторах?**
- **Pointer-free ноды** (uint32-смещения) → GC scan ≈ 0, cache locality.
- **CSR-layout** для замороженных сегментов при dim≤256 → +14% QPS (cache locality соседей).
- **SQ8-квантование** (float32→int8) для frozen-сегментов → 4× компрессия памяти, ~96% recall,
  выше QPS за счёт L3-локальности. Файл: `vector/frozen_sq.go`.
- **AVX2 FMA** для distance (`distance_amd64.s`).
- **LSH pre-filter** для больших размерностей (`lsh.go`).

**Q: Как выбирал параметры HNSW?**
- M=32, efConstruction=400 — дефолты. efSearch=100 — **рабочая точка**: recall@10≈0.966 на
  MNIST-784, при этом ~1.56× QPS против efSearch=200 (где recall 0.983). То есть за +1.7% recall
  платишь 1.56× скорости — невыгодно. Это я померил, см. `vector/step_profit_test.go`.
- Здесь сильный ответ: «Я не угадывал параметры — я их **измерил** на recall/QPS-кривой.»

**Q: Фильтрованный поиск (категоризация) — как?**
- `VSIM.SEARCHFILTER` (`main.go:1290`). Метаданные хранятся обычными KV-ключами
  (`category:product:123` → `electronics`). Поиск принимает замыкание `filterFn`, которое
  идёт во все сегменты. Это та же функция `search`, просто `filterFn != nil`. Мультитенантность
  строится тем же приёмом — фильтр по префиксу ключа + изоляция по слотам кластера.

### 3.5 Сеть / zero-alloc

**Q: Почему epoll, а не goroutine-per-connection?**
- При 10k+ соединений goroutine-per-conn = много стеков и планировщик потеет. Epoll: по
  event-loop на воркер, греедивый drain сокета. Файл: `internal/server/epoll.go`.

**Q: Откуда 37× прирост на пайплайне?**
- Три строки: `Buffered()` + цикл по командам из одного TCP-пакета + один `Flush()`. Это убрало
  TCP round-trip на каждую команду — он и был главным bottleneck. GET P=128 → 2.42M RPS
  (`docs/optimization_session_summary.md`). Честный вывод: «Самая большая победа была не в
  хитром алгоритме, а в устранении сетевого round-trip.»

### 3.6 WASM / Compute

**Q: Зачем WASM, а не Lua как в Redis?**
- Изоляция (песочница — crash модуля ≠ crash сервера), переносимость, и можно писать логику на
  любом языке (Go/Rust → wasm). Использую wazero (чистый Go, без CGO).
- Reactor-паттерн: worker-local слоты инстансов, чтобы не инстанцировать модуль на каждый вызов.
  Оптимизация дала 14ms → 4.9ms → 3ms (parallel), убрав `fmt.Sprintf`/`time.Now` с горячего
  пути и переиспользуя инстансы. Файлы: `internal/compute/{runtime,worker_slot,trigger}.go`,
  док `docs/compute_benchmarks.md`.

### 3.7 Кластер

**Q: Как шардируешь и роутишь ключи?**
- 16384 hash-слота, CRC16 (совместимо с Redis Cluster). Клиент получает `-MOVED`/`-ASK`
  редиректы. Gossip для обнаружения нод (PING/PONG, failure detection: pfail через 10с, fail
  через 30с), leader election при падении мастера. Live-миграция слотов. Файлы: `internal/cluster/`.

## 4. Каверзные вопросы (trade-offs)

**Q: Где это сломается под нагрузкой? Назови bottleneck.**
- Честно: на single-key hot path упираюсь не в store, а в TCP/epoll/syscall — GET P=128 не рос
  при смене аллокатора, потому что store уже не был узким местом. Для векторов узкое место —
  компакция L2+ (секунды), поэтому я и вынес её в фоновый build-pool, чтобы не блокировать
  вставку. Backpressure через bounded queue (32) защищает от OOM.

**Q: LSM даёт write/read amplification. Тебя это не пугает?**
- Это сознательный trade-off: плачу read-amplification (search идёт по нескольким сегментам)
  ради дешёвой вставки и иммутабельности (lock-free reads). Компенсирую параллельным поиском по
  сегментам и слиянием уровней (fanout=4 ограничивает число сегментов ~log4(N)).

**Q: Tombstones же раздувают индекс. Когда чистятся?**
- При слиянии сегментов мёртвые ключи физически выпадают. Если поток удалений высокий — это
  ускоряет компакцию. Метрика `VectorTombstoneTotal` мониторит объём.

**Q: efSearch ×4 при фильтрации — а если фильтр очень селективный (1 из 100k)?**
- Тогда даже ×4 окна мало и recall падает — это known limitation post-filtering. Правильное
  решение — pre-filtering (LSH-bucket по фильтру) или отдельный индекс на категорию; у меня
  есть LSH-каркас, но честно: для очень селективных фильтров pre-filtering предпочтительнее.

**Q: Почему не использовал готовую библиотеку (FAISS, hnswlib)?**
- Цель была — единый Go-бинарник без CGO и внешних зависимостей, с собственным контролем памяти
  (zero-GC) и интеграцией в общий движок (WAL, кластер, TTL на векторы через CompositeEvictor).
  Готовая библиотека не дала бы этой интеграции и pointer-free контроля над GC.

**Q: Consistency модель кластера? Это CP или AP?**
- Ближе к AP с eventual consistency: gossip + асинхронная репликация мастер-реплика. Сильной
  согласованности (Raft) пока нет — это в roadmap (Enterprise). Признаю честно: split-brain при
  сетевом разделении возможен, защита — failure detection с таймаутами, но не консенсус.

## 5. Слабые места — говорить честно

Признание ограничений = senior-сигнал. Подготовленные формулировки:

- **Нет Raft/консенсуса** — репликация асинхронная, возможна потеря последних записей при падении
  мастера. В roadmap как Enterprise-фича.
- **Post-filtering у векторов** проседает на очень селективных фильтрах (см. выше).
- **WASM instance pooling** — sync.Pool инстансов был запланирован; reactor-слоты частично
  решают, но cold-start модуля всё ещё заметен.
- **Single-writer на dim** — векторный стор фиксирует размерность глобально (одна коллекция).
  Мульти-коллекции — это следующий шаг.
- **Бенчмарки сняты на одной машине** (i7-9750H) — не распределённый стресс-тест на проде.

## 6. Поведенческие вопросы (STAR — на базе проекта)

**«Расскажи о технически сложной задаче.»**
- **S/T:** Вставка вектора блокировала search, потому что HNSW — единая мутабельная структура.
  Под burst-write latency search прыгала.
- **A:** Применил LSM-подход: вставка в append-only delta, фоновая компакция в иммутабельные
  сегменты, поиск без локов по снапшоту. Пришлось решить TCMalloc data race (изолированные
  аллокаторы на воркер) и TOCTOU с Clear (epoch-проверка).
- **R:** Вставка стала O(1) и перестала блокировать чтение; search идёт параллельно по сегментам.

**«Расскажи об оптимизации, которой гордишься.»**
- Pipeline: три строки кода (`Buffered`+loop+`Flush`) дали 37× на GET (65K → 2.42M RPS).
  Урок: сначала измерь, где реальный bottleneck (был TCP round-trip), потом оптимизируй —
  иначе полируешь не то.

**«Где ошибся / что бы сделал иначе?»**
- Сначала гонял за микрооптимизациями аллокатора, хотя профайл показывал, что узкое место — сеть.
  Вывод: профилирование до оптимизации. Теперь каждый перф-PR подкреплён бенчмарком (regression
  latency = P0).
